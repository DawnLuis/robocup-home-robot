## 一、背景：第一阶段被扣 1000 分的两类问题

赛事规则规定：抽出的题目中每有一题出现语法错误或格式错误，扣该队总分 500 分；
少交一题同样扣 500 分。赛前审核阶段，第一阶段赛题被判定 2 道题不合规，合计扣 1000 分，
问题类型为：

| # | 问题 | 应为 | 实际（整改前） |
|---|------|------|----------------|
| 1 | 阶段开关 | 第一阶段 `mis/err/ans` 均为 `off` | `mis="on"` |
| 2 | 容器描述字段顺序 | `(sort *)(size *)(at *)(type * container)(opened\|closed *)` | `(sort *)(size *)(type * container)(closed *)(at *)`（`at` 写在 `type` 之后） |

这两条直接决定了本轮整改的方法论：**题面标准以出题指南与比赛规则为唯一依据**，
逐条编码为可执行检查，不依赖任何其他来源的经验推断。

## 二、提交规范（依据赛事规则 §2.7 二）

- 题目以**压缩包**形式提交；**题目文件命名格式为 `<抽签顺序>-<题目顺序>`**（如 `7-01.xml`）。
- 参赛代码压缩包**主文件夹统一命名为 `<抽签顺序>-<学校>-<队伍名称>`**，内含代码与题目两个压缩包。
- 提交截止后裁判组**从每队 30 道题中随机抽取 2 道**汇总成题库逐题审核 ——
  因此 30 道题必须**每一道**都合规，不存在"部分题安全"的策略。
- 审题阶段有**半小时各队自我调试时间**用于发现题目的逻辑问题。

据此新增 `scripts/robocup-打包.sh`，按上述命名与结构生成提交包，避免现场命名出错。

## 三、第一阶段赛题整改

### 3.1 阶段开关

第一阶段统一为 `mis="off" err="off" ans="off"`，第二阶段统一为 `mis="on" err="on" ans="on"`
（指南 §二.1 / 规则 §2.7 三(2)）。开关同时影响平台行为：

- `mis="off"` 时 `<mis>` 段内容会随环境下发（`getEnv4Plug` 仅在 `is_missing` 为真时屏蔽）；
- `err="off"` 时下发给机器人的是 `<r>`（正确信息）而非 `<w>`。

因此第一阶段将 `<mis>`、`<err>`、`<extra>` 三段留空，所有信息置于 `<info>`，
既符合"第一阶段信息完全正确"的定位，也避免空段与开关组合产生的歧义。

### 3.2 容器描述字段顺序

容器在 `info` 中的字段统一为：

```
(sort N <容器名>) (size N big) (at N <位置>) (type N container) (closed N | opened N)
```

即 `at` 必须在 `type` 之前。全部 60 道题的容器行经脚本核对，顺序异常 0 行。

### 3.3 `inside` 指令的条件集合

按附录B 逐字比对，`(:info (inside X Y))` 与 `(:cons_notnot (:info (inside X Y)))` 的条件为：

```
(:cond (sort X *) (color X *) (sort Y *))
```

**不含** `(type Y container)`。带 `type` 的仅 `putin`/`takeout` 的 `Y` 与 `open`/`close` 的 `X`。
整改前有 9 个模板（涉及第一阶段 7 道题）在 `inside` 上多写了 `(type Y container)`，已删除。

## 四、第二阶段赛题整改

### 4.1 信息组织方案与实测对比

第二阶段允许信息缺失与信息错误。整改前方案将 2 个小物体的位置分别摘出 `info`
（一个置于 `mis` 段、一个置于 `err` 段）；整改后方案（当前采用）将 `mis` 段留空、
所有小物体位置保留在 `info`，仅 `err` 段保留一处误导位置。

依据：指南 §二.3 表述为"`mis` 部分**可以**有……"（允许而非必须）；§二.2 注(2) 的
"字段可以省略"以"该字段出现在 `mis`/`err`/`extra` 部分"为前提，位置保留在 `info`
则字段完整性一律满足。第二阶段的难度由 `err` 的误导位置与 `ans=on` 时的交互不确定性维持。

**客户端实机对比**（自出题 30 道，NT 模式，各 2 轮）：

| 方案 | 第 1 轮 | 第 2 轮 | 均值 |
|------|---------|---------|------|
| 旧（位置藏于 `mis`） | 5144 | 5238 | 5191 |
| 新（位置全在 `info`） | 5538 | 5618 | **5578** |

两轮区间不重叠，差值 **+387 分**（30 题）。逐题对比为上升 20 题 / 下降 8 题（后者为
第二阶段固有的运行多态，幅度 ±4~20）。原因：旧方案每题多一个"位置完全未知"的物体，
客户端只能通过 `AskLoc` 询问（每次 −2 分，且 `ans=on` 时存在约 30% 的错误回答概率）。

### 4.2 错误信息不得制造死局

`err` 段的 `<w>` 会作为机器人视角的初始信息下发。若 `<w>` 把物体放进"被约束要求
保持关闭的容器"，机器人依此取物就必须开门，从而破坏约束 —— 该题在机器人视角下无解。

实例：某题 `<w>` 将绿瓶置于 `cupboard` 内，而同题 `cons_notnot` 要求 `cupboard`
始终保持 `closed`；官方 validator 在该题上耗尽 90 秒仍无法求解（穷举证明无解）。
整改后生成器内置规则：**`<w>` 不得指向被 `cons_notnot(closed X)` 或
`cons_not(:task (open X))` 保护的容器**。

## 五、合规检查体系

出题指南与比赛规则中可编码为规则的要求，逐条实现为检查器（`scripts/`）：

| 脚本 | 检查内容 |
|------|----------|
| `check_appendixB_2026.py` | 逐条指令与附录B模板比对（条件集合+顺序）、容器描述语法、阶段开关、§三.6 两小物体 |
| `check_syntax_2026.py` | XML 良构、各段括号平衡、附录A 字段顺序、指令结尾括号数（cons 4 / 其他 3）、谓词白名单、X/Y 变量 |
| `check_rules_2026.py` | 编号/断号、字段完整性、重复物体、重复指令、理论满分上限、NL 句数与句号 |
| `check_cons_init.py` | 约束初始满足性（被破坏 = 题面缺陷） |
| `check_submit_2026.py` | NL 与指令逐句对应（附录C 句型）、**NL 小物体颜色描述**、同行字段 id 一致、理论满分核算 |
| `check_stage2_2026.py` | 第二阶段 `mis`/`err`/`extra` 三段规则、`r/w` 组合、`w` 与 `info` 一致性、`instr` 的 `info` 与真实环境一致 |
| `robocup-终检.sh` | 一键串联上述 8 项，供赛前快速自查 |
| `run_validate.sh` | 调用官方 validator 批量校验（语法 + ASP 可解性） |

其中"NL 小物体颜色描述"来自规则 §2.7 三(2)：`info`、`instr`、`nl` 三处凡涉及小物体
都必须有对应的颜色描述。检查器的有效性以"人为去掉颜色的样本"回归验证。

## 六、官方 validator 的行为分析

使用平台自带 `tools/validate_tests`（validator + cserver）批量校验时，观察并实验确认：

1. **validator 构造的 ASP 状态 = `info` + `err` 的 `<w>`，不读取 `<mis>` 段。**
   对照实验：同一道题，位置置于 `<mis>` 时 ASP 状态文件中该物体无位置、求解 60 秒超时；
   将同样内容移入 `<info>` 后瞬间通过、状态文件中出现该位置事实。
2. 因此 `<mis>` 段承载小物体位置时，位置在 validator 视角下"未知"，ASP 需枚举其
   所有可能位置，导致组合爆炸 —— 这是旧方案 30 题中 23 题超时的唯一原因，
   与题面语法或逻辑无关。
3. **`unvalid` 的三种成因需区分**：真 UNSAT（`Execution failed`，题面逻辑矛盾）、
   ASP 超时（求解窗口不足）、格式/解析错误。判据上只有真 UNSAT 属题面缺陷。

整改前后（第二阶段 30 题）：`valid 7 / unvalid 23`（总耗时 30–40 分钟）→
`valid 30 / unvalid 0`（总耗时 24.3 秒），真 UNSAT 均为 0。

## 七、理论满分核算

指南 §五与规则 §2.5 二规定：单题理论满分 = `40×目标数 + 20×约束数 − 行动扣分 + 效率分`，
须落在 200–1000；`info` 句为补充信息，不计入目标/约束数；核算时效率分记 100。

核算方法：官方 validator 的 `testlog.txt` 会输出 ASP 求得的可行行动序列
（`occurs(move(7),1) occurs(pickup(7),2) ...`）。`testDevil.lp` 未设 `#minimize`，
该方案未必最优，故由其算出的 `40G+20C+100 − 行动扣分` 是理论满分的**下界**，`≥200` 即安全。

| 阶段 | 理论满分（参考） | 上限 |
|------|------------------|------|
| 第一阶段 | 206 ~ 260 | 240 ~ 300 |
| 第二阶段 | 216 ~ 258 | 240 ~ 300 |

两阶段全部满足 §五 的 200–1000 区间。

## 九、剩余风险

- 自然语言中的**功能词**（`from` / `of` / `the` 等连接词）无法从现有文件严格证明其属于
  词汇表：规则文件中没有独立的自然语言词汇表章节，附录C 对 `takeout` 仅给出
  `take ... out`。当前判断为合法（否则 `takeout` 句式无法表达容器），属判断而非证明。
- 人工审核对"题目逻辑合理性"的口径无法穷尽枚举；已知的逻辑类硬要求
  （约束初始态、任务可解性、错误信息不制造死局、`instr` 的 `info` 与环境一致）均已覆盖。
- 审题阶段提供的半小时自我调试时间可作为最终复核窗口，届时用 `robocup-终检.sh` 复跑。
