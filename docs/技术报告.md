## 一、项目定位

中国机器人大赛 · 服务机器人仿真项目。3D 仿真家庭机器人，程序用 9 种原子行动序列完成任务，
按效率评分。两个子项目：

- **IT**（指令语言）：平台直接给 `(:ins ...)` 结构化指令
- **NT**（自然语言）：给受限英语句子，需 NLU 转结构化指令

比赛分两个阶段：第一阶段 `ans=off` 初始信息完全正确；第二阶段 `mis/err/ans=on`，
初始状态可能出错、用户回答也可能错误或不知道。

除参赛程序外，每队每阶段须提交 30 道题目（未提交无抽题资格），题目质量同样计入总分
（每题语法/格式错误扣 500 分，少交一题扣 500 分）。

**参赛代码**：`~/Downloads/robocup-home-robot`（GitHub，SSH 推送，单一 `example/` 目录，
IT/NT 靠 `-mode it|nt` 切换，`Plan()` 检测 `(:ins` 前缀跳过 NLU）
**本地平台**：`~/Downloads/Planner-release-2025/Planner-release-ubuntu18/`

## 二、运行环境与构建

**比赛环境 = Ubuntu（非 Arch）**。平台 `src/` 在 Ubuntu 原样可编译（不需 Arch 的 Boost 1.92
移植）；参赛代码 `example/` 跨平台。`iclingo` 是 32 位预编译二进制，Ubuntu 需装 `libc6-i386`
等 32 位支持库。

本地 Arch 环境（zen 内核 7.1.11，Boost 1.92）需做 Boost 1.92 移植才能编译 `src/`（6 处）：

- `platform.hpp`：`boost::asio::io_service` → `io_context`
- `platform.cpp`：`asio::io_service&` → `io_context&`；`new asio::io_service` → `io_context`；
  `asio::deadline_timer` → `asio::steady_timer`（`std::chrono::seconds(1)`）
- `plug.cpp`：`io_service` → `io_context`；`address_v4::from_string` → `make_address`

构建与运行：

```bash
sudo pacman -S boost   # 依赖 Boost 1.48+
cd .../build && cmake .. && make -j$(nproc)
cd ../bin && mkdir -p log && cp -p ../res/iclingo ../res/*.lp .
chmod +x iclingo       # 必须！32位静态二进制，cp后常丢+x，丢失则所有行动返回 false、全场 0 分
./cserver -td ../tests/example -eval ../lib/libasp -log log -mode it -test all
# 另开终端: ./example    跑完看 log/Dawnluis.log
```

自动化工具：

- `scripts/run_suite.sh <测试目录> <标签> <轮数>`：多轮自动跑分 + 存盘（NT 模式）
- `scripts/run_it.sh`：同上，IT 模式
- 端口占用用 `pkill -x cserver` 清理（★精确匹配，`-f cserver` 会命中执行命令的 shell 自身）

**坑 12（最隐蔽）**：系统时钟跳变时 `make` 报"时钟错误"仍显示"Built target"但根本没重编。
判据：改源码后确认 `bin/example` 时间戳刷新 + `.o` 重编译。**变体**：`.o` 路径是
`build/example/CMakeFiles/example.dir/*.o`（不是 `build/CMakeFiles/...`），rm 错路径会静默用旧 binary。

## 三、系统架构

```
include/cserver/plug.hpp        ← 客户端框架：Plug基类 + 9原子行动 + AskLoc + Sense
example/main.cpp                ← 入口，调用 Devil::Plan()
example/devil.cpp               ← 规划主逻辑（Plan + 各任务执行函数）
example/environment_manager.cpp ← 环境状态解析与更新（Env 状态机）
example/instruction_parser.cpp  ← :ins 结构化指令解析
example/nlu.cpp                 ← NT 英文 → 结构化指令（SimpleNLU）
bin/cserver                     ← 平台服务器（127.0.0.1:7932）
bin/example                     ← 编译产物客户端
lib/libasp.so                   ← 评分库
res/iclingo                     ← ASP 求解器（平台用它验证每个行动的合法性）
```

### 3.1 原子行动

`Move(x) PickUp(a) PutDown(a) ToPlate(a) FromPlate(a) Open(a) Close(a) PutIn(a,b) TakeOut(a,b)`；
`AskLoc(a) → "not_known" | "at(a,b)" | "inside(a,b)"`（★无空格，以 `evaluate.cpp` 的
`wrong_as()` 拼接为准，`plug.hpp` 注释格式有误）；`Sense(vec)` 返回 id 列表。

每个行动平台返回 bool（执行条件不满足=false），**返回值即免费的 ASP 真值神谕**。

### 3.2 评分公式

```
基础分 = 40×完成目标 + 20×维护约束(须完成≥1目标才计约束分) − 4×move − 2×(人机交互+其他物理) − 1×观察
效率分 = 2×⌈(规定时间−结束时间)×10⌉ × sgn(完成目标)
单题理论满分 200-1000；超过 1000 按 1000 计，负分按负分计；两阶段总分排名
```

### 3.3 评分规则关键细节（`evaluate.lp` + 平台源码实锤）

- `evaluate.lp` 第 41 行：`:- occurs(pickup(A),1), h(plate(A),0)` —— 物体在盘上时执行
  `pickup(A)` 直接非法
- `fromplate(A)`（57-63 行）：盘上取物的唯一合法动作，要求物体在盘上 + 空手
- **`fortask.lp` 第 17 行**：`goal(takeout(A,B),0) :- not h(inside(A,B),0)` ——
  **takeout 是负目标**：物体不在 B 内即已满足，此时做动作反而全白扣分
- 容器门 `closed` 时不能 `putin`/`takeout`；`open`/`close` 要求空手且与容器同位置
- Move 按次数计费（每次固定 −4，与距离无关）

## 四、阶段格式与信息语义

### 4.1 阶段开关

依出题指南 §二.1 与比赛规则 §2.7 三(2)：**第一阶段 `mis/err/ans` 三者均为 `off`，
第二阶段三者均为 `on`**。

开关同时决定平台行为：

- `mis="off"` 时 `<mis>` 段内容会随环境下发（`getEnv4Plug` 仅在 `is_missing` 为真时屏蔽）；
- `err="off"` 时下发给机器人的是 `<r>`（正确信息）而非 `<w>`。

因此第一阶段将 `<mis>`、`<err>`、`<extra>` 三段留空，所有信息置于 `<info>`。

★ **易踩的坑**：平台自带的第一阶段题库几乎全部写作 `mis="on"`。**裁判依据的是出题指南
与比赛规则，而非平台题库的既有写法** —— 按平台题库反推格式会导致扣分（详见第七章）。

### 4.2 err 的 r/w 语义真相（平台源码实锤）

`platform.cpp` 解析：`<r>` → `correct_info`，`<w>` → `erroneous_info`

- `getEnv4Grader()`（评分）= info + missing_info + **correct_info(r)** + extra_info
- `getEnv4Plug()`（传给机器人）= info + (is_missing ? "" : missing_info) + **erroneous_info(w)**

即第二阶段：**机器人拿到的是 `<w>`（错误位置），评分用的是 `<r>`（正确位置）**。
与出题指南字面（r=错误 / w=正确）相反，以平台源码为准。出题时 `err` 段必须写成
`r=正确位置, w=错误位置`，否则评分与机器人所见的颠倒，整题失效。

验证：平台自带 `stage2/50.xml` 的 err 为 `r=(inside 8 2)... w=(at 8 1)...`，
传给机器人的 env 是 `(at 8 1)...`（=w），评分用 r。

### 4.3 AskLoc 撒谎机制与 Sense 视野（`evaluate.cpp` 实锤）

- `mislead` 标志 = xml 的 `ans="on"`（`platform.cpp:743` 解析）
- `ans=off` 时 AskLoc 100% 返回正确答案（`if(!mislead) return right_answer`）
- `ans=on` 时调用 `wrong_as()`：**60% 正确 / 30% 错误 / 10% not_known**，
  错误答案从环境的 `at_loc`/`in_loc` 中随机挑选
- AskLoc 一次 −2 分；Sense 一次 −1 分且**从不撒谎**（无 mislead 分支，直读 ASP 解集）
- Sense 视野（`evaluate.lp` 134-135）：只报与机器人同位置的地面物 + 同位置 **opened**
  容器内的物；看不到异地物、closed 容器内物，且分不清地面物与开容器内物
- `srand(time(0))` 仅在 `Evaluate` 构造时调用 → 同一 cserver 进程内多题共享 rand 序列，
  这是第二阶段逐题波动（±35 分）的来源之一，A/B 必须多轮取均值

### 5.2 核心修复详解

**6.1 takeout 三修复（09-04，commit 1fc99ec）**

*修复 1：`execute_takeout_task` 条件解析 bug（收益最大）*

旧代码对每条 X/Y 条件都直接调用查找函数。遍历到 `(color X white)` 时，
`str_to_object_type("white")` 返回 `Unknown(24)`，再查找返回 −1，**把先前找到的正确
obj_id 覆盖掉**；`(type Y container)` 同样把 container_id 覆盖为 −1。

后果：**NT 模式带 color/type 条件的 takeout 任务永远"无法找到任务所需的物体"**，
整类任务 0% 完成。修法：先按 attr 收集 x_type/x_color/y_type，循环结束后各查一次。

教训：遍历 conds 做查找时必须按 attr 过滤，否则非 sort 条件（color/type）经
`str_to_object_type` 转成 Unknown 后会覆盖正确结果。

*修复 2：takeout 负目标语义（`fortask.lp` 第 17 行实锤）*

物体只要不在 B 内目标即已满足，做动作反而全白扣分。正确逻辑：

- 物体位置已知且不在 B 内 → 零动作直接收分
- 位置未知 → AskLoc 查明：真在 B 内才做 TakeOut；不在 → 零动作收分
- putin/puton 的中间步 takeout 需要手持物体（`need_in_hand=true`），失败时转真实容器/PickUp

*修复 3：`update_from_askloc` 支持 `inside(a,b)`*

防御式设计：仅当物体完全无已知位置时才写入；`askloc_set` 标记位置来源；
`forget_position()` 在动作失败证伪位置线索时清除 + 重查一次（`allow_reask=false` 限次防死循环）；
绝不覆盖 env 已有位置。

**6.2 NLU 句式修复（09-04，commit a791b40）**

*修复 1：takeout 句式 "out of" 识别* —— `96.xml` 的 NL 为
`Take the bottle which is red out of the refrigerator.`，旧代码 task 分支中 takeout 判断
排在 puton/putin 之后，"out of" 句式不含 "put" 关键词但被默认 puton 兜底吞掉。
修法：takeout 判断**提前到 putin/puton 之前**，支持 `take out`/`get out`/`take...out of`/

**6.3 Sense 验尸实验（09-04，否决回退）**

方案：AskLoc 查明位置 → 到位后 Sense(−1) 验证 → 证伪则 forget 重摇。

否决理由 1（数据）：平台 stage1 也有 mis 物体（位置未知 → 触发 AskLoc → 触发 Sense），
但 stage1 `ans=off` 时 AskLoc 全真话 → Sense 必然验证通过 = 纯烧分 + ASP 耗时拖累效率分。

否决理由 2（原则）：stage1/2 对机器人不可区分，无可靠自动探测手段；比赛代码必须自适应
（赛事方统一运行提交的二进制，无人替选手切换阶段）。

### 6.4 goto 任务最后执行（10-16，commit 0f297a5）

**问题**：`goto` 的目标判定是 `goal(goto(B), t) :- h(sameloc(B), t)` —— **终止状态**在目标位置。
而 `Plan()` 原本按 `instr` 顺序执行任务，`goto` 夹在搬运任务中间，其后的 Move 把机器人带离
目标位置，该目标即失效，**每题白丢 40 分**。

**实测铁证**：18-02/03/04/05（同一模板组）的收尾动作均为
`... Move 5(goto) → Move 9 → PickUp 9`。反推分数 `174 = 40×3 + 20×1 − 34(动作) + 68(效率)`，
`G=4` 却只按 3 个目标计分，差值恰为一个目标（40 分）。

**改法**：`Plan()` 中任务分三组并依次执行

```
tasks（普通搬运任务） → state_tasks（open/close 状态任务） → goto_tasks（goto）
```

`goto` 必须排在 `state_tasks` 之后 —— open/close 同样需要 Move 到容器处，否则也会带离目标位置。

**A/B 对账**（自出题 30 道，NT 模式，同版本）：

| 阶段 | 旧基线 | 新基线 | 净变化 | 涨/跌 |
|------|--------|--------|--------|-------|
| stage1 | 6222 / 6224 | 6464 / 6462 | **+242** | 涨 7 题 / 跌 0 题 |
| stage2 | 5462 | 5830 / 5872 | **+368** | 涨 12 题 / 跌 1 题 |

stage2 唯一"跌"的 18-29（−20）无 `goto` 任务，旧代码两轮亦在 196~216 间波动（固有运行多态），
新代码两轮稳定为 196/196，非系统性退步。

**方法论**：目标的语义决定执行顺序 —— "终止状态"类目标（如 `goto` 的 `sameloc`）必须最后执行；
"过程状态"类约束（`cons`）则要求从初始到终止每一步都满足。本仓库题目中 19/30 含 `goto`
（为抬升理论满分而补充），因此该改动的收益面较大。

### 6.5 pickup 任务误走 TakeOut 的失败兜底（10-16，commit 244b92a）

**问题**：`execute_pickup` 中"env 认为物体在容器内 → 打开容器 + TakeOut"这一分支，TakeOut 失败后
**直接 `return false`，没有任何退路**。而 env 认定的"在容器内"可能来自 `err` 的 `<w>` 假线索，
或 AskLoc 的错误回答 —— 于是一次失败就让整个 pickup 任务作废：目标丢失，且已付出的动作分白扣。

实测（18-02 stage2）收尾动作为 `Move 3 → TakeOut 9 3|false`，之后再无任何动作。

值得注意：**同一函数里另外两处**（位置未知时 AskLoc 得到容器、PickUp 失败后重查得到容器）
调用 `execute_takeout` 时本就有兜底，唯独这条"直接 TakeOut"的路径漏了。
排查同类缺陷的有效手法是**横向对比同一函数内相似路径的完备程度**。

**改法**：失败后套用 `execute_takeout` 的兜底模式 —— `forget_position` + 重查一次
（由 `allow_reask` 限定，不会递归）：

- 重查结果在**别的容器** → 转 `execute_takeout`（不再 reask）
- 重查结果在**地面** → 改走 `execute_pickup`（不再 reask）
- 重查结果仍是**同一容器** → 放弃

**A/B 对账**（自出题 30 道，NT 模式，各 2 轮均值）：

| 阶段 | 旧基线 | 新基线 | 净变化 | 涨/跌 |
|------|--------|--------|--------|-------|
| stage1 | 6463 | 6462 | 持平（−1，波动内） | 阶段一位置信息真实，该分支不触发 |
| stage2 | 5851 | 5955 | **+104** | 涨 8 题（+5~+30）/ 跌 4 题（−6~−11） |

跌项源于兜底会触发 `AskLoc`（`ans=on` 时 30% 撒谎 → 掷骰子），故轮间出现波动；净收益显著为正。

**可选后续优化**：兜底中那次 `AskLoc` 可以省去 —— `TakeOut` 失败本身已证伪"在该容器内"，
直接改走 `PickUp` 更省（−2 分）且无随机性。当前净收益已为正，暂未实施。

| 3 | 候选硬过滤导致整条目标丢失 | 受保护候选被一律硬过滤，若为**唯一候选**则整条目标丢 40 分 | 改为按代价打分排序，**无干净候选时选代价最小者**（净 +40−20 > 0 优于放弃） | 94.xml 230→256、98.xml 186→208 |
| 4 | puton 缺候选重试循环 | putin 有（≤6 次），puton 没有，首选被过滤即整任务失败 | 补对称循环 | 同上 |
| 5 | 超时被强杀后污染后续题 | 平台 5s 超时发 Fini 并切断，客户端仍继续发动作、状态未收拾 → **污染后续每一题**（实测 G=14 单跑 410 分，跟超时题后连跑 **−4 分**） | `Plan()` 起始计时，三个任务循环在开新任务前检查，超 4.35s 主动收工 | 自造大题集 1382→1774（+392） |
| 6 | 零动作收分覆盖不全 | 目标判定只看最终状态，但"已满足则短路"有缺口 | 补 `puton` / `pickup`（在盘上）/ `give`（已在 human 处） | 官方 s1 8642→8812、s2 7136→7584 |

另有一项低风险优化：**给 goto 任务预留时间预算** —— goto 只花 1 个 Move（≈0.1s）却值 40 分，
且按语义必须最后执行，时间不够时最先被牺牲。自造 G=14 大题 13336→13678（+342）。

**★ 关键认识：零动作收分。** `res/fortask.lp` 的 9 种目标全部是"最终状态判定"：

```
goal(puton(A,B),0)   :- h(sameplace(A,B),0), h(outagent(A),0)
goal(give(human,A),0):- h(sameplace(A,B),0), h(outagent(A),0)
goal(pickup(A),0)    :- not h(outagent(A),0)
goal(putdown(A),0)   :- h(outagent(A),0)
goal(goto(B),0)      :- h(sameloc(B),0)
goal(open(B),0)      :- h(opened(B),0)     goal(close(B),0) :- h(closed(B),0)
goal(putin(A,B),0)   :- h(inside(A,B),0)   goal(takeout(A,B),0) :- not h(inside(A,B),0)

h(sameplace(A,B),0) :- h(at(A,X),0), h(at(B,X),0)      h(sameloc(B),0) :- h(at(B,X),0), h(at(0,X),0)
h(outagent(A),0)    :- not h(hold(A),0), **not h(plate(A),0)**
```

因此"开局即已达成"的目标应当**零动作收分**。此前实现只判断了"手"，漏了"盘"——
这一缺口正是现场"同题别队 942 分 / 本队 780 分"差距的主要来源：942 分反推约 12 个动作，
780 分反推约 45 个动作；而比赛时所用版本尚无任何零动作收分逻辑。

**方法论沉淀**：同类问题的排查手法是**横向对比同族路径的完程度**（`putin` vs `puton` 的候选循环、
`execute_takeout` vs `pickup` 捷径的开门判断）——本轮 3 处缺陷都是这样定位的。

## 六、赛题出题：规范与整改

### 6.1 背景：第一阶段被扣 1000 分的两类问题

赛前审核阶段，第一阶段赛题被判定 2 道题不合规，合计扣 1000 分：

| # | 问题 | 应为 | 实际（整改前） |
|---|------|------|----------------|
| 1 | 阶段开关 | 第一阶段 `mis/err/ans` 均为 `off` | `mis="on"` |
| 2 | 容器描述字段顺序 | `(sort *)(size *)(at *)(type * container)(opened\|closed *)` | `(sort *)(size *)(type * container)(closed *)(at *)`（`at` 写在 `type` 之后） |

这两条确立了本轮整改的方法论：**题面标准以出题指南与比赛规则为唯一依据**，
逐条编码为可执行检查，不依赖任何其他来源的经验推断。

### 6.2 提交规范（依据赛事规则 §2.7 二）

- 题目以**压缩包**形式提交；**题目文件命名格式为 `<抽签顺序>-<题目顺序>`**（如 `7-01.xml`）。
- 参赛代码压缩包**主文件夹统一命名为 `<抽签顺序>-<学校>-<队伍名称>`**，内含代码与题目两个压缩包。
- 提交截止后裁判组**从每队 30 道题中随机抽取 2 道**汇总成题库逐题审核 ——
  因此 30 道题必须**每一道**都合规。
- 审题阶段有**半小时各队自我调试时间**用于发现题目的逻辑问题。

据此新增 `scripts/robocup-打包.sh`，按上述命名与结构生成提交包。

### 6.3 第一阶段赛题整改

**① 阶段开关**：统一为 `mis="off" err="off" ans="off"`，并将 `<mis>`、`<err>`、`<extra>`
三段留空，所有信息置于 `<info>`，契合"第一阶段信息完全正确"的定位。

**② 容器描述字段顺序**：

```
(sort N <容器名>) (size N big) (at N <位置>) (type N container) (closed N | opened N)
```

即 `at` 必须在 `type` 之前。60 道题的容器行经脚本核对，顺序异常 0 行。

**③ `inside` 指令的条件集合**：按附录B 逐字比对，`(:info (inside X Y))` 与
`(:cons_notnot (:info (inside X Y)))` 的条件为 `(sort X *) (color X *) (sort Y *)`，
**不含** `(type Y container)`；带 `type` 的仅 `putin`/`takeout` 的 `Y` 与 `open`/`close` 的 `X`。
整改前有 9 个模板（涉及第一阶段 7 道题）在 `inside` 上多写了 `(type Y container)`，已删除。

### 6.4 第二阶段赛题整改

**① 信息组织方案与实测对比**

第二阶段允许信息缺失与信息错误。整改前方案将 2 个小物体的位置分别摘出 `info`
（一个置于 `mis` 段、一个置于 `err` 段）；整改后方案（当前采用）将 `mis` 段留空、
所有小物体位置保留在 `info`，仅 `err` 段保留一处误导位置。

依据：指南 §二.3 表述为"`mis` 部分**可以**有……"（允许而非必须）；§二.2 注(2) 的
"字段可以省略"以"该字段出现在 `mis`/`err`/`extra` 部分"为前提，位置保留在 `info`
则字段完整性一律满足。

**客户端实机对比**（自出题 30 道，NT 模式，各 2 轮）：

| 方案 | 第 1 轮 | 第 2 轮 | 均值 |
|------|---------|---------|------|
| 旧（位置藏于 `mis`） | 5144 | 5238 | 5191 |
| 新（位置全在 `info`） | 5538 | 5618 | **5578** |

两轮区间不重叠，差值 **+387 分**。逐题对比为上升 20 题 / 下降 8 题（后者为第二阶段
固有的运行多态，幅度 ±4~20）。原因：旧方案每题多一个"位置完全未知"的物体，客户端只能
通过 `AskLoc` 询问（每次 −2 分，且 `ans=on` 时约有 30% 的错误回答概率）。

**② 错误信息不得制造死局**

`err` 段的 `<w>` 会作为机器人视角的初始信息下发。若 `<w>` 把物体放进"被约束要求保持
关闭的容器"，机器人依此取物就必须开门，从而破坏约束 —— 该题在机器人视角下无解。

实例：某题 `<w>` 将绿瓶置于 `cupboard` 内，而同题 `cons_notnot` 要求 `cupboard` 始终
保持 `closed`；官方 validator 在该题上耗尽 90 秒仍无法求解。整改后生成器内置规则：
**`<w>` 不得指向被 `cons_notnot(closed X)` 或 `cons_not(:task (open X))` 保护的容器**。

### 6.5 第二阶段加坑设计（2026-10-16，commit 45d00c5 / 2dde192）

自查发现：原自出 stage2 题 G 仅 3~4、C 仅 0~2（理论满分 200~300），而官方题库 G 达 7、C 达 6
—— **本队出的题比官方还小，等于给对手送分**。

新生成器 `scripts/gen_stage2_traps.py` 输出 30 题 **G=14 / C=6 / 理论满分 780**。
坑位全部是"机制级"的（不依赖对方规划是否聪明），并逐条守住出题指南与赛事规则：

| 坑 | 机制 | 合规依据 | 本方免疫 |
|----|------|----------|----------|
| A 大题化 | 搬运任务动作下界 4n，而 5s 时限只够约 52 个动作（n≤13）；G=14 时被超时强杀，**未做收工防护的客户端会卡死并连锁污染后续每一题** | 指南 §五 满分 200~1000 | 已修超时自计时收工 |
| B goto 乱序 | goto 插在搬运任务中段：按 instr 顺序执行的客户端，goto 达成后又被后续 Move 带离目标位置 → 白丢 40 分/题 | 附录B 无执行顺序要求 | 已修 goto 最后执行 + 时间预留 |
| C mis/err | mis 藏 1 个物体位置（须 AskLoc，−2 分/次），err 给 r=正确 / w=错误 的误导位置 | §二.3 mis 段"可以有" | 已有动作失败后重查 |

**刻意放弃的坑（合规红线，实测被检查器拦下）**：

- 存在量词目标（如 "Put a book on the bed" 不带 color）→ 指南 §四 要求凡涉及小物体必须带颜色描述，
  检查判定 30/30 不符
- `cons_notnot(plate X)` → 语义有歧义（检查器把"所有同类物体"都要求满足，报初始破坏约束）
- w 指向被禁开容器 → 会造成机器人视角下无解（死局），违反"w 不得制造死局"

**场景随机化**：初版 30 题的物体位置都写成 `at == 自身编号`、goto 固定出现在第 6 行，
人工裁判一眼可辨为模板产物 → 引入 `scene_pos(seed)`（每题一套位置）+ goto 插入位 4~8 随机。

**实测效果（同一套 30 题，2026 官方平台）**：
最初代码 **1828 分 / 6 题**（含 2 个负分，之后整体卡死）
vs 当前代码 **13622~13742 分 / 30 题**。

**合规验证**：提交前终检 8 项全绿；另做 **16 项指南逐条独立对照**（含开关、编号连续、位置非负、
附录A 三类字段序、一个位置至多一个大物体、不可出现完全一样的大/小物体、不得重复 task/cons、
括号平衡、cons_notnot 内层、指令内小物体带 color、nl 句数与句号、nl 小物体带颜色、满分区间）
全部通过。官方 validator 的 unvalid 经确认全部是 ASP 求解超时（G=14 目标组合空间过大，
60s 窗口不足），`Execution failed` 计数为 0，即无真 UNSAT。

### 6.6 压力测试：理论满分 1000 的题能跑多少（`scripts/gen_big1000.py`）

生成 G=18 / C=9 / 理论满分 1000 的题，分密集型（部分目标初始即满足）与稀疏型两类。

| 题目 | 旧代码 | 当前代码 |
|------|--------|----------|
| big1000-01（密集） | 352 | 392（4.18s） |
| big1000-02（密集） | 332 | 406（4.27s） |
| big1000-03（稀疏） | 0（超时强杀） | 260（4.37s） |
| big1000-04（稀疏） | 0（超时强杀） | 280（4.38s） |
| 合计 | 684 | 1338 |

**结论：上限 1000 的题跑不到 900。** 这是算术约束：

```
900 = 40G + 20C + 效率分 − 行动扣分   →  G=18,C=9 时需要「效率分 = 行动扣分 + 0」
行动扣分：18 个搬运任务 = 72 个动作起步，5s 只够 52 个 → 至少扣 150~200 分
效率分上限：100 分（且 72 个动作需 6.9s > 时限 → 实际效率分为 0）
∴ 该规模下分数天花板约 400~550
```

密型（部分目标零动作收分）392~406，已是该规模下的最优形态；疏型 260~280。

### 7.2 官方 validator 的行为分析

使用平台自带 `tools/validate_tests`（validator + cserver）批量校验时，经实验确认：

1. **validator 构造的 ASP 状态 = `info` + `err` 的 `<w>`，不读取 `<mis>` 段。**
   对照实验：同一道题，位置置于 `<mis>` 时 ASP 状态文件中该物体无位置、求解 60 秒超时；
   将同样内容移入 `<info>` 后瞬间通过、状态文件中出现该位置事实。
2. 因此 `<mis>` 段承载小物体位置时，位置在 validator 视角下"未知"，ASP 需枚举其所有
   可能位置，导致组合爆炸 —— 这是旧方案 30 题中 23 题超时的唯一原因，与题面语法或逻辑无关。
3. **`unvalid` 的三种成因需区分**：真 UNSAT（`Execution failed`，题面逻辑矛盾）、
   ASP 超时（求解窗口不足）、格式/解析错误。只有真 UNSAT 属题面缺陷。

整改前后（第二阶段 30 题）：`valid 7 / unvalid 23`（总耗时 30–40 分钟）→
`valid 30 / unvalid 0`（总耗时 24.3 秒），真 UNSAT 均为 0。

### 7.3 理论满分核算

指南 §五与规则 §2.5 二规定：单题理论满分 = `40×目标数 + 20×约束数 − 行动扣分 + 效率分`，
须落在 200–1000；`info` 句为补充信息，不计入目标/约束数；核算时效率分记 100。

核算方法：官方 validator 的 `testlog.txt` 会输出 ASP 求得的可行行动序列
（`occurs(move(7),1) occurs(pickup(7),2) ...`）。`testDevil.lp` 未设 `#minimize`，
该方案未必最优，故由其算出的 `40G+20C+100 − 行动扣分` 是理论满分的**下界**，`≥200` 即安全。

| 阶段 | 理论满分（参考下界） | 上限 |
|------|----------------------|------|
| 第一阶段 | 206 ~ 260 | 240 ~ 300 |
| 第二阶段 | 216 ~ 258 | 240 ~ 300 |

## 十二、剩余风险与下一步

**赛题侧剩余风险**

- 自然语言中的**功能词**（`from` / `of` / `the` 等连接词）无法从现有文件严格证明其属于
  词汇表：规则文件中没有独立的自然语言词汇表章节，附录C 对 `takeout` 仅给出 `take ... out`。
  当前判断为合法（否则 `takeout` 句式无法表达容器），属判断而非证明。
- 人工审核对"题目逻辑合理性"的口径无法穷尽枚举；已知的逻辑类硬要求（约束初始态、
  任务可解性、错误信息不制造死局、`instr` 的 `info` 与环境一致）均已覆盖。
- 审题阶段提供的半小时自我调试时间可作为最终复核窗口。

**参赛程序侧下一步**（6.4~6.6 条目已标记完成状态）

本轮已完成：

- ~~`cons_notnot` 保护边界~~ → 6.6 #1（解析层 13 字符修正后，保护逻辑首次真正生效）
- ~~pickup 失败兜底~~ → 6.5
- ~~goto 任务排序~~ → 6.4 + goto 时间预留（6.6 附加项）
- ~~零动作收分覆盖~~ → 6.6 #6（9 种 goal 均已实现"已满足则短路"）

剩余事项：

1. **兜底中的 AskLoc 可省**：`TakeOut` 失败本身已证伪"在该容器内"，直接改走 `PickUp` 更省
   （−2 分）且无 `ans=on` 时的随机性（详见 6.5 末）
2. **`find_object_by_type` 不区分物体状态**（同类型多物体时可能选错），可参照
   `find_object_by_conditions` 的打分排序思路改造
3. **任务依赖排序** —— ★ **本轮实测负收益，须谨慎**：按"动作成本"重排任务顺序在 G=14 大题上
   为 **−1030 分（跌 22 题）**。根因是 `is_reserved_by_specific_task`（`try_held_object` 中的
   物体预留判断）**扫描的是"后续任务"**，天然依赖任务顺序；任何重排必须先把它改造为
   "看全体任务"而非"看后续任务"，否则会打乱物体分配。**任务顺序是与物体预留/候选选择/约束维护
   耦合的隐式契约，不可随意重排。**
4. **开门冗余可省一个动作**：`Move物 PickUp物 Move容器 PutDown Open PickUp PutIn`（7 动作）
   可改为 `Move容器 Open Move物 PickUp Move容器 PutIn`（6 动作）—— 分数相同但省 1 个动作
   （官方 s1 共 21 处，约 +42 分效率分）。风险/收益比不佳，未实施。
5. **ToPlate 双持搬运**：手 + 盘同时携带两个物体、一次 Move 完成两个任务（收益待评估；
   注意 `goal(puton(A,B))` 要求 `outagent(A)`，故 puton 不能用 ToPlate 收尾）
6. **stage2 代码侧已接近榨干**：官方 NT-stage2 达成率约 46%，扣分结构为目标/约束损失 4724、
   行动扣分 2144、效率分损失 1692；可回收碎肉仅约 70 分（重复 AskLoc 28 分 + `not_known`
   后直接放弃 40 分）。根本难处：`GetEnvDes()` 把 `info` 与 `err` 的 w 拼成同一个字符串，
   客户端**无法区分哪个位置可疑**，只能"先试、失败后重查"；而 AskLoc 自身在 `ans=on` 时
   也有 30% 撒谎，先查不一定比先试划算。
