## 一、项目定位

中国机器人大赛 · 服务机器人仿真项目。3D仿真家庭机器人，程序用9种原子行动
序列完成任务，按效率评分。两个子项目：

比赛分两个阶段（第一阶段 ans=off 初始信息正确；第二阶段 mis/err/ans=on

## 三、系统架构

```
include/cserver/plug.hpp   ← 客户端框架：Plug基类 + 9原子行动 + AskLoc + Sense
example/main.cpp           ← 入口，调用 Devil::Plan()
example/devil.cpp          ← 规划主逻辑（Plan + 各任务执行函数）
example/environment_manager.cpp ← 环境状态解析与更新（Env状态机）
example/instruction_parser.cpp ← :ins 结构化指令解析
example/nlu.cpp            ← NT英文 → 结构化指令（SimpleNLU）
bin/cserver                ← 平台服务器（127.0.0.1:7932）
bin/example                ← 编译产物客户端
lib/libasp.so              ← 评分库
res/iclingo                ← ASP求解器（平台验证行动合法性）
```

### 原子行动
`Move(x) PickUp(a) PutDown(a) ToPlate(a) FromPlate(a) Open(a) Close(a)
PutIn(a,b) TakeOut(a,b)`；`AskLoc(a)→"not_known"|"at(a,b)"|"inside(a,b)"`
（★无空格，以 evaluate.cpp wrong_as() 拼接为准，plug.hpp 注释格式有误）；
`Sense(vec)` 返回 id 列表。每行动平台返回 bool（条件不满足=false，
返回值即免费 ASP 真值神谕）。IT 模式 ts 字段=`(:ins ...)` 结构化；
NT 模式=受限英语句子。

### 评分公式
```
基础分 = 40×完成目标 + 20×维护约束(须完成≥1目标才计约束分) − 4×move − 2×(人机+物理) − 1×观察
效率分 = 2×⌈(规定时间−结束时间)×10⌉×完成目标数
单题满分 200-1000，两阶段总分排名
```

### 评分规则关键细节（evaluate.lp + 平台源码实锤）
- **evaluate.lp 第41行**：`:- occurs(pickup(A),1), h(plate(A),0)` —— 物体在
  盘上时执行 `pickup(A)` 直接非法
- `fromplate(A)`（57-63行）：盘上取物唯一合法动作，要求物体在盘上+空手
- **fortask.lp 第17行**：`goal(takeout(A,B),0) :- not h(inside(A,B),0)` ——
  **takeout 是负目标**：物体不在 B 内即满足，做动作反而全白扣
- 容器门 closed 时不能 putin/takeout；open/close 要求空手且同位置

## 四、阶段格式事实（平台实测）

- **第一阶段 Stage1 = `mis="on" err="off" ans="off"`**（不是指南字面的全off）。
  mis 段放小物体初始 at/inside 位置（正常信息），err 为空，ans 正常。
- **第二阶段 Stage2 = `mis="on" err="on" ans="on"`**（mis错位+err错误值+ans
  可能答错）。

★ **err 的 r/w 语义真相（平台源码实锤）**：
- `platform.cpp` `getEnv4Grader()`（评分）= info + missing_info + **correct_info(r)**
  + extra_info → **评分用 r=正确值**
- `getEnv4Plug()`（传给机器人）= info + ... + **erroneous_info(w)** → err="on"
  时机器人拿到 **w=错误值（误导）**
- **与出题指南字面（r=错误/w=正确）正好相反！** 以平台源码为准：r=正确/评分，
  w=错误/误导机器人。出题时 err 段必须写成 **r=正确位置, w=错误位置**，否则
  评分和机器人看到的颠倒，题全废。

★ **AskLoc 撒谎机制（evaluate.cpp 实锤）**：
- `mislead` 标志 = xml `ans="on"`（platform.cpp:743 解析）
- ans=off 时 AskLoc 100% 返回正确答案（`if(!mislead) return right_answer`）
- ans=on 时调用 `wrong_as()`：**60%正确 / 30%错误 / 10%not_known**；错误答案
  从环境 at_loc/in_loc 随机拼接
- AskLoc 一次 -2 分；Sense 一次 -1 分且从不撒谎（无 mislead 分支，直读 ASP 解集）
- Sense 视野（evaluate.lp 134-135）：只报与机器人同位置的地面物 + 同位置
  **opened** 容器内的物。看不到异地、closed 容器内物

## 六、核心修复详解

### 6.1 takeout 三修复（09-04, commit 1fc99ec）

**修复1：execute_takeout_task 条件解析 bug（收益最大）**

旧代码对每条 X/Y 条件都直接调 `find_object_by_conditions`/`find_object_by_type`。
当遍历到 `(color X white)` 条件时，`str_to_object_type("white")` 返回 `Unknown(24)`，
再 `find_object_by_conditions(24)` 返回 -1，**把先前找到的正确 obj_id 覆盖掉**；
`(type Y container)` 同样把 container_id 覆盖为 -1。

后果：**NT 模式带 color/type 条件的 takeout 任务永远"无法找到任务所需的物体"**，
整类任务 0% 完成。IT 模式不受影响（不走 NLU，但 task 分发同样命中此 bug 的
execute_takeout_task 函数——IT 的 instr 已带正确 type/color 条件但代码仍重复查找）。

修法：先按 attr 收集 x_type/x_color/y_type，循环结束后各查一次。

教训：遍历 conds 做查找时必须按 attr 过滤，否则非 sort 条件（color/type）经过
`str_to_object_type` 转成 Unknown 后会覆盖正确结果。

**修复2：takeout 负目标语义（平台源码 fortask.lp 第17行实锤）**

`goal(takeout(A,B),0) :- not h(inside(A,B),0)` —— 物体只要不在 B 内，目标即已
满足，做动作反而全白扣分。

正确逻辑：
- 物体位置已知且不在 B 内 → 零动作直接收分（return true）
- 位置未知（mis 场景）→ AskLoc 查明：真在 B 内才做 TakeOut；不在 → 零动作收分
- putin/puton 的中间步 takeout 需要手持物体（`need_in_hand=true`），失败时转真实容器/PickUp

此修复解释了之前两次 AskLoc 兜底翻车的根因：拿地面物硬做 TakeOut 白费动作。
负目标语义下，"不在容器内"就是目标达成，不该做任何动作。

**修复3：update_from_askloc 支持 inside(a,b)**

防御式设计：
- 仅当物体完全无已知位置（valid_at/valid_inside/on_plate/held_by_robot 全 false）时才写入
- `askloc_set` 标记记录位置来源是否为 AskLoc
- `forget_position()` 在动作失败证伪位置线索时清除 + 重查一次（`allow_reask=false` 限次防死循环）
- 绝不覆盖 env 已有位置（err 的 w 假线索不可被 AskLoc 假答案二次覆盖）

### 6.2 NLU 句式修复（09-04, commit a791b40）

**修复1：takeout 句式 "out of" 识别**

96.xml NL: `Take the bottle which is red out of the refrigerator.`

旧代码 task 分支中 takeout 判断排在 puton/putin 之后，"out of" 句式不含 "put"
关键词但被默认 puton 兜底吞掉。修法：将 takeout 判断**提前到 putin/puton 之前**，
支持 `take out`/`get out`/`take...out of`/`take...from` 句式。

**修复2：must 约束句不再误入 task 分支**

77/90/93/97.xml NL: `The refrigerator must not be opened.`

旧代码 task 分支入口仅排除 `opened`/`closed` 关键词，但 "must not be opened"
含 "open" 动词被 task 分支抢走 → 误生成 `cons_not(task open)`，正确应为
`cons_not(info opened)`。修法：task 分支入口加 `!is_required`，含 must/should/always
的约束句不再误入 task。

安全性验证：全题库扫描无 "must+任务动词" 句式（must 句均为状态约束），should/always
零命中。

**回归验证**：使用 `scripts/nlu_regress.py` 全量比对客户端 NLU 输出 vs 题目 expected instr。
46/48 题输出逐字节不变，96/97 修正。IT 模式不经过 NLU，7810 分毫不差。
剩余差异定性：28 题为 container type 伪差异（按指南方案 A 预期），其余为 example 题自身
NL/instr 矛盾。

### 6.3 Sense 验尸实验（09-04，否决回退）

**方案**：AskLoc 查明位置 → 到位后 Sense(-1) 验证 → 证伪则 forget 重摇。

**否决理由1（数据）**：平台 stage1 也有 mis 物体（位置未知→触发 AskLoc→触发 Sense），
但 stage1 ans=off AskLoc 全真话 → Sense 必然验证通过 = 纯烧分 + ASP 耗时拖累效率分。
实测每题整齐 -6，平台 s1 8050→7889（-160）。自出 stage2 均值 4905 vs v5 4919 持平
（收益被 Sense 成本吃光，仅 PickUp|false 从 10.5→4.75 减半）。

**否决理由2（原则）**：stage1/2 对机器人不可区分（err 假值看不出是假的，文件名可能
重名），无可靠自动探测手段。比赛代码必须自适应（赛事方统一运行提交的二进制，无人
替选手切换阶段），开关方案在真实比赛中不可操作。

**结论**：Sense 在当前题目机制下无任何能自动获益的场景。v5（1fc99ec）为本轮最终版。
副产品知识：Sense 永不说谎（直读 ASP 解集无 mislead 分支），视野=同位置地面物 +
同位置开门容器内物，分不清地面 vs 开容器内。

## 八、err 的 r/w 语义真相

`platform.cpp` 解析：`<r>`→correct_info, `<w>`→erroneous_info
- `getEnv4Grader()`（评分）= info + missing_info + **correct_info(r)** + extra_info
- `getEnv4Plug()`（传给机器人）= info + (is_missing?"":missing_info) +
  **erroneous_info(w)**

即 stage2：机器人拿到 w（错误位置），评分用 r（正确位置）。与出题指南字面
（r=错误/w=正确）相反，以平台源码为准。出题时 err 段必须写成 r=正确, w=错误。

验证：平台自带 stage2/50.xml err `r=(inside 8 2)... w=(at 8 1)...`，
传机器人 env=`(at 8 1)...`=w，评分用 r。

## 九、出题方法论与记录

### 规范题出题方法论
- **手写30个完整自洽模板 > 自动随机生成**：每个模板同时产出 env + instr + nl，
  三者引用同一份物体分配（obj 含 sort/color/ctype），保证一致
- **致命坑**：instr/nl 必须从同一物体分配生成。硬编码颜色然后"换色变体"
  而 instr/nl 没同步换 → NL/instr 错位
- 生成后自检三件套：①check_rules2.py 查格式合规 ②md5sum 去重 ③NLU 回归

### 第一阶段 30 题（08-31 完成）
- 位置 tests/stage1/18-01~30.xml，mis=on err=off ans=off
- 容器任务全带 (type X/Y container)（方案 A，按出题指南）
- 三重验证：合规 30/30，md5 去重 30/30，平台执行 30/30 无 0 分
- 生成器：scripts/gen_stage1.py

### 第二阶段 30 题（08-31 完成）
- 位置 tests/stage2/18-01~30.xml，mis=on err=on ans=on
- 3 小物体分配：第0个→mis，第1个→err（r=正确/w=错误），第2个→info
- 生成器：scripts/gen_stage2.py
- 三重验证全过

### 容器 type 条件结论（方案 A）
出题指南明确"容器类任务条件带 (type X container)"，平台自带例题多不带。
按出题指南 → 方案 A（容器任务带 type，严格合规）。理由：交题不合规每题扣 500 分，
比赛抽的是规范题。NLU 对所有容器谓词生成 type，不区分 negated。
