## 一、项目定位

中国机器人大赛 · 服务机器人仿真项目。3D仿真家庭机器人，程序用9种原子行动
序列完成任务，按效率评分。两个子项目：
- **IT**（指令语言）：平台直接给 `(:ins ...)` 结构化指令
- **NT**（自然语言）：给受限英语句子，需 NLU 转结构化指令

比赛分两个阶段（第一阶段 ans=off 初始信息正确；第二阶段 mis/err/ans=on
初始信息可能错误，需 AskLoc/Sense 验证重规划）。

**参赛代码**：`~/Downloads/robocup-home-robot`（GitHub，SSH 推送，仓库内
`example/IT/` 与 `example/NT/` 两套参赛代码）

## 二、运行环境与构建

**比赛环境 = Ubuntu（非 Arch）**。src/ 平台代码在 Ubuntu 原样可编译（不需
Arch 的 Boost 1.92 移植）；参赛代码 example/ 跨平台。iclingo 是 32 位预编译
二进制，Ubuntu 需装 libc6-i386 等 32 位支持库。

本地 Arch 环境（zen 内核 7.1.11, Boost 1.92）需做 Boost 1.92 移植才能编译
src/（6 处）：
- `platform.hpp`：`boost::asio::io_service` → `io_context`
- `platform.cpp`：`asio::io_service&` → `io_context&`；`new asio::io_service` → `io_context`；
  `asio::deadline_timer` → `asio::steady_timer`（`std::chrono::seconds(1)`）
- `plug.cpp`：`io_service` → `io_context`；`address_v4::from_string` → `make_address`

构建与运行：
```bash
sudo pacman -S boost   # 依赖 Boost 1.48+
cd .../build && cmake .. && make -j$(nproc)
cd ../bin && mkdir -p log && cp -p ../res/iclingo ../res/*.lp .
chmod +x iclingo       # ★必须！32位静态二进制，cp后常丢+x
./cserver -td ../tests/example -eval ../lib/libasp -log log -mode it -test all
# 另开终端: ./example    跑完看 log/Dawnluis.log
```
自动化：`bin/run_tests.sh all|it|nt`、`bin/run_single.sh <it|nt>`。端口占用用
`pkill -f cserver` 清理。

**坑12（★最隐蔽）**：系统时钟跳变时 make 报"时钟错误"仍显示"Built target"
但根本重编。判据：改源码后确认 `bin/example` 时间戳刷新 + `.o` 重编译。
**变体**：`.o` 路径是 `build/example/CMakeFiles/example.dir/*.o`（不是
`build/CMakeFiles/...`），rm 错路径会静默用旧 binary。C++注释不编译进
binary，不能用 strings 验证注释串，需用时间戳或实际跑分验证。

## 三、系统架构

```
include/cserver/plug.hpp   ← 客户端框架：Plug基类 + 9原子行动 + AskLoc + Sense
example/main.cpp           ← 入口，调用 Devil::Plan()
example/devil.cpp          ← 规划主逻辑（Plan + 各任务执行函数）
example/environment_manager.cpp ← 环境状态解析与更新（Env状态机）
example/instruction_parser.cpp ← :ins 结构化指令解析
example/nlu.cpp            ← NT英文 → 结构化指令（SimpleNLU）
bin/cserver                ← 平台服务器（127.0.0.1:7932）
bin/example                ← 编译产物客户端
lib/libasp.so              ← 评分库
res/iclingo                ← ASP求解器（平台验证行动合法性）
```

### 原子行动
`Move(x) PickUp(a) PutDown(a) ToPlate(a) FromPlate(a) Open(a) Close(a)
PutIn(a,b) TakeOut(a,b)`；`AskLoc(a)→"not_known"|"(on a b)"|"(inside a b)"`；
`Sense(vec)`。每行动平台返回 bool（条件不满足=false）。IT模式 ts 字段=
`(:ins ...)` 结构化；NT 模式=受限英语句子。

### 评分公式
```
基础分 = 40×完成目标 + 20×维护约束(须完成≥1目标才计约束分) − 4×move − 2×(人机+物理) − 1×观察
效率分 = 2×⌈(规定时间−结束时间)×10⌉×完成目标数
单题满分 200-1000，两阶段总分排名
```

### 评分规则关键细节（evaluate.lp + 平台源码实锤）
- **evaluate.lp 第41行**：`:- occurs(pickup(A),1), h(plate(A),0)` —— 物体在
  盘上（plate(A)为真）时执行 `pickup(A)` **直接非法**，平台返回 false
- `fromplate(A)`（57-63行）：盘上取物的**唯一合法**动作，要求物体在盘上+空手
- `toplate(A)`（49-55行）：要求手持 → 把手中物体放上盘
- 容器门 closed 时不能 putin/takeout；open/close 要求空手且同位置
- 环境 `(hold 14)(plate 15)` 开头，hold=0 表示空手（代码映射为 -1）

## 四、阶段格式事实（平台实测）

- **第一阶段 Stage1 = `mis="on" err="off" ans="off"`**（不是指南字面的全off）。
  平台 problems/{IT,NT}/stage1 全部如此。mis 段放小物体初始 at/inside 位置
  （正常信息），err 为空，ans 正常。
- **第二阶段 Stage2 = `mis="on" err="on" ans="on"`**（mis错位+err错误值+ans
  可能答错）。

第一阶段环境 domain 以 `(hold X)` 开头，然后是 `(plate Y)`，之后各
`(sort id type)` `(size ...)` `(at ...)` `(inside ...)` `(color ...)`
`(type ... container)` `(closed/opened ...)`。

★ **解析顺序陷阱**：`(plate Y)` 在 domain **开头**，早于 `(sort ...)`。
parse_predicate 处理 plate 时对象尚未创建，`on_plate` 不会被设上。已修复：
`parse_from_domain_string` 末尾统一补设（遍历 plate_objects）。

★ **err 的 r/w 语义真相（平台源码实锤）**：
- `platform.cpp` `getEnv4Grader()`（评分）= info + missing_info + **correct_info(r)**
  + extra_info → **评分用 r=正确值**
- `getEnv4Plug()`（传给机器人）= info + ... + **erroneous_info(w)** → err="on"
  时机器人拿到 **w=错误值（误导）**
- **与出题指南字面（r=错误/w=正确）正好相反！** 以平台源码为准：r=正确/评分，
  w=错误/误导机器人。出题时 err 段必须写成 **r=正确位置, w=错误位置**，否则
  评分和机器人看到的颠倒，题全废。

## 七、NLU 修复记录（08-31 已实现）

NT 7158→7298，NLU 输出 vs expected instr 匹配率 0/48→24/48：
- **Bug A**：task 分支 open/close 谓词 opened/closed→open/close
- **Bug B**：info 分支改精确句式（is closed/opened/in/on/near/there is/not
  opened/not closed）而非裸"door of"；info 分支放 task 前 → "close door of X"
  为 task(close)，"is closed" 不被误判 task
- **Bug C**：cons_not 内层用 is_task_origin 标记（非猜句子）
- **Bug D+F**：plate 关键字 → (plate X) 谓词，覆盖 cons_notnot/info
- **Bug E**：give 特殊处理，从 objects 去 human
- **Bug G**："is not opened"→closed，"is not closed"→opened（信息取反非 cons_not）
- **教训★**：分支顺序必须 cons_notnot→info→task→negated。task 放 info 前会让
  "is closed" 误判 task(close) 分数降，重构回 info 在前恢复。

**第二轮修复（匹配率 23→24）**：①info 分支 relation_map 遍历前先查
"is opened"/"is closed"（否则"washmachine"里的"in"子串误判 inside）②task
分支入口加 `!contains(opened)&&!contains(closed)` 防"must not be opened"
状态句被当 task(open) ③negated 分支加 plate 条件识别"must not be on plate"
→cons_not(plate)。

**第三轮修复（为规范题，30/30 匹配）**：①移除容器 type 生成的 `!is_negated`
限制 → cons_not/cons_notnot 内层容器任务也生成 type ②inside 谓词的 Y 若为
容器也补 type ③**word_contains 替代 contains 做 relation_map 遍历（★关键）**：
"closet"含"close"子串，contains 会把 "in the closet" 误判成 closed；三处
relation_map 遍历都改 word_contains（整词匹配，"next to"等多词 key 有效）。

**匹配率瓶颈真相**：剩余不匹配多为 example 题 NL/instr 本身矛盾（NL 说 can 但
instr 写 bottle、缺 color/type），非 NLU bug。真实比赛抽规范题，不必纠结
example 字符串匹配。

**测试污染教训★**：改 tests/example 影响评分标准；评估 NLU 必须用原始
tests/problems/NT/stage1 题；平台目录非 git 无版本保护；要版本管理的是 GitHub
上的 example/ 参赛代码。

## 十、cons_notnot 解析 bug + 主动满足（已回退）

- **解析 bug 根因**：`(:cons_notnot` 以 `(:cons_not` 开头被当单重否定；且它是
  **13字符**（非12），substr(12) 会留个 't'；parse_rule 里 `(:info` 先匹配导致
  is_double_neg 分支永不触发。修法：①parse_instructions 先判断 `(:cons_notnot`
  并 substr(13) ②parse_rule 把 is_double_neg 判断提到 `(:info`/`(:task` 前。
- **主动满足实测负收益★**：新增 execute_fact_task 把 FactRequired 转成
  puton/putin 执行，NT 7620→7302 下降。原因：cons_notnot 说"X must be on Y"
  初始多半已满足，但无条件执行引入多余动作（PickUp/PutOn/冲突）扣分>约束维护
  加分。**结论：不主动满足 cons_notnot，靠正常任务隐式满足**。已回退全部改动。
- cons_notnot 正确解析为 FactRequired 本身仍值得（供 check_constraints 用），

## 十一、on_plate 生命周期 bug（★本次核心，已修复）

### 根因
`update_after_pickup`（environment_manager.cpp:488）和 `update_after_putdown`
都**没清 `on_plate`** 标记。

### 后果链
1. 物体在盘上 → `on_plate=true`（domain 开头补设）
2. 机器人 `FromPlate` 拿起它 → `update_after_pickup` 只清 valid_inside/
   valid_at，**on_plate 仍是 true**
3. 物体已不在盘上，但标记仍 true
4. 后续再次 pickup 该物体（putin 流程"放下→开门→重新拿起"，
   见 execute_putin_task）→ devil.cpp:989 `if (obj->on_plate)` 误判 → 走
   FromPlate → 物体不在盘上 → **FromPlate 返回 false，任务失败**

### 70.xml 实锤（修复前得分80，最低）
```
环境: (plate 18) (hold 10)  任务含 "Put a can in the closet"
动作序列: ... [FromPlate 18|true] [Move 7] [PutDown 18] [Open 7] [FromPlate 18|false]
```
第二次 `FromPlate 18|false` 即 on_plate 未清除所致。

### 修复内容
`environment_manager.cpp` 5 个 update_after_* 同步维护 `on_plate`：
- `update_after_pickup`：+`on_plate=false`（★核心）
- `update_after_putin` / `update_after_puton` / `update_after_takeout`：同样清
- `update_after_putdown`：注释说明不重设（放下位置非盘时已由 pickup 清除）

### A/B 对照结果（权威，逐题对账）
| 指标 | 值 |
|------|-----|
| 基线 NT | 7578 |
| 修复后 NT | 7608（第1次）/ 7606（第2次复现）|
| 净收益 | **+30~32** |
| 关键题 70.xml | 80 → **116（+36）** ★确定性修复 |
| 其余波动 | 93/85/96 各-2，复现后漂移（85+2, 84/99-2），纯运行波动 |
| IT 模式 | 7870（48/48 全得分）|

### 修复后 70.xml 验证
- 修复前：`[Open 7][FromPlate 18|false]` ← 盘上物二次拿起走错分支失败
- 修复后：`[Open 7][PickUp 18|true][PutIn 18 7|true]` ← on_plate 已清，正确
  PickUp，任务成功完成

### 影响范围
所有含盘上物体+二次拿起流程的题（putin/puton 需中途放下的）。54/61/64/70/
74/80/93/94/95 都含 FromPlate。

## 十四、已识别问题清单

### P1：on_plate 生命周期 bug（★已修复，见十一）
### P2：AskLoc 返回 inside 格式被丢弃
`update_from_askloc`（environment_manager.cpp:417-484）只认 `at(id,loc)`，
遇到 `inside(a,b)`（AskLoc 文档明确支持）直接返回"格式错误"。但第一阶段
ans=off 时 AskLoc 对盘上物返回 at，对容器内物才返回 inside，大部分场景 at
够用。**需确认是否有题因 inside 解析缺失而低分**。（★历史教训：加 inside
解析曾实测 -270 负收益并回退，本项需谨慎，可能不适用。）
### P3：TakeOut 失败无兜底（77.xml 得136）
`execute_takeout` 失败后仅打印调试信息，不尝试 AskLoc 或重规划。第一阶段
